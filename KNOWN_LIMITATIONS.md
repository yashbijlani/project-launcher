# Known limitations

This project favors refusing or asking over guessing. These limitations are known and
evidence-backed for the V2 implementation.

## Runtime and supervision

- There is no persistent supervisor daemon.
  - Each CLI invocation constructs a manager.
  - Persistence comes from state files, ownership locks, and process groups.
  - Live events exist only while the HTTP server is running.
- Ownership uses process groups, not kernel cgroups.
  - A launcher-owned cgroup would be a stronger boundary, but cgroup v2 delegation is
    not portable across the target environments and can require elevated setup.
  - V2 compensates with PID + kernel-start-time identity and identity-gated signaling.
  - A process that deliberately daemonizes or escapes its process group may survive.
- Starting an application can create its normal runtime/cache artifacts inside that
  repository. The launcher does not edit source, configuration, dependencies, or Git
  history, but it cannot suppress files generated by the supervised application.
- Verification starts real services.
  - That is the only way to prove health, so verification is not free.
  - It is gated by prerequisites, unsafe approval, ownership, and cleanup confirmation,
    and it never installs dependencies or modifies repositories.
- Containers were not exercised end-to-end.
  - The Docker CLI is present but the daemon was unavailable.
  - A safe Compose fixture and a guarded lifecycle test exist but were skipped.
- No public exposure controls were tested.
  - The UI binds to loopback by default, but service commands themselves determine
    their bind addresses.

## Discovery

- Discovery is intentionally shallow.
  - It can miss unconventional layouts, generated projects, and deeply nested packages.
  - Workspace globs are expanded explicitly, but arbitrary nesting is not walked.
- Workspace monorepos still need human selection.
  - The launcher lists runnable targets; it cannot know which package is "the project".
- Infrastructure-only Compose files are recognized, but cross-runtime readiness is
  limited.
  - The launcher can order its own processes and read Compose health conditions, but it
    cannot make an external database healthy.
- Dependencies are never installed automatically.
  - Missing dependencies are reported as blockers with suggestions.
- Ports and URLs are heuristics.
  - Conventional Vite/Next/FastAPI values may be wrong for customized projects.
  - FastAPI now suggests `/docs`, but a framework-aware health endpoint is still a
    suggestion, not proof.
- Command classification is heuristic.
  - Failure labels help triage; they are not a formal diagnosis.

## Verification

- Verification proves that the configuration worked at a point in time on this machine.
  - It is not a guarantee that it will work after environment changes (dependency
    updates, moved interpreters, freed/occupied ports).
  - Environment versions are recorded but are not part of the fingerprint, so an
    environment change does not automatically invalidate verification.
- The fingerprint covers startup-relevant configuration only.
  - Cosmetic edits (notes, metadata) do not invalidate.
  - It includes id and root, so identical service definitions in different projects do
    not share fingerprints.
- A verified project can still fail later (port conflicts, credentials expiring,
  external services disappearing). Verification reduces uncertainty; it does not remove it.

## Ownership and safety

- Locking is per project, not per service.
  - Two projects that happen to share a port can still conflict; that is reported as a
    port conflict at start, not prevented by the lock.
- Stale-lock recovery uses a heartbeat window. A long-blocked launcher whose heartbeat
  expires can have its lock recovered while it is technically alive.
- The unsafe heuristic is evidence-based, not exhaustive.
  - It catches explicit vulnerable-target markers, privileged Compose patterns,
    deployment layouts, devices, and destructive/AI-proposal patterns.
  - It cannot prove an unfamiliar repository is safe.
- The API has no authentication.
  - Anyone able to reach the loopback port can invoke operations. Unsafe projects still
    require a typed reason, but safe projects do not.

## Desktop, hotkey, and UI

- The dashboard is a local web UI, not a packaged native application.
- The WebKitGTK desktop window and the Hyprland hotkey were not exercised in this
  session; they remain integration code.
- SSE event delivery to a long-lived browser client was not asserted in tests.

## AI and learning

- No AI provider was configured; `ai-propose` was not exercised against a live model.
- Proposal validation is layered and rejects dangerous patterns, but prompt-injection
  resistance of an arbitrary external model was not evaluated.
- AI-invented commands are only warned about, not blocked; they still require approval
  and should be verified before routine use.
- `learn` mode observes only processes under a selected project root.
  - It requires Linux `/proc`.
  - It cannot reliably reconstruct shell intent from forks alone.
  - Learned commands always require review before use.

## Security and privacy

- Service logs can contain secrets emitted by applications.
  - Local logs are not redacted; only outbound AI evidence is redacted.
  - Logs are never sent to AI by default.

## What should come next

The highest-value work is systemic, not cosmetic:

1. Validate the Docker Compose lifecycle against the safe fixture on a machine with a
   running daemon.
2. Investigate opt-in cgroup v2 ownership where delegation is available, keeping process
   groups as the portable fallback.
3. Add environment fingerprinting that is strict enough to matter but not so strict that
   harmless updates invalidate verification.
4. Add live SSE assertions and a headless UI smoke test.
5. Extend readiness with explicit, user-approved setup actions (never automatic).
