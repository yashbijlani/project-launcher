# Known limitations

This prototype intentionally favors refusing or asking over guessing. The following limitations
are known and evidence-backed.

## Runtime and supervision

- There is no persistent supervisor daemon.  - Each CLI invocation constructs a manager.
  - Persistence comes from state files, leases, and process-group ownership.
  - This works for start/stop/restart, but there is no continuous cross-process event stream.
- Process cleanup tracks detached process groups, not kernel cgroups.
  - Well-behaved children are cleaned reliably.
  - A process that deliberately daemonizes or escapes its process group may survive.
- Starting an application can create its normal runtime/cache artifacts inside that repository.
  The launcher does not edit source, configuration, dependencies, or Git history, but it cannot
  suppress files generated by the supervised application itself.
- Containers were not tested.
  - Docker Compose startup, volume behavior, and container shutdown remain unvalidated.
  - The local Docker daemon was unavailable during the experiment.
- No public exposure controls were tested.
  - The UI binds to loopback by default, but service commands themselves determine their bind addresses.

## Discovery

- Discovery is intentionally shallow.
  - It can miss unconventional layouts, generated projects, and deeply nested packages.
  - That is preferable to loading entire repositories.
- Workspace monorepos still need human selection.
  - The launcher can identify candidates and warn about scope, but cannot know which package
    the user considers “the project.”
- Infrastructure-only Compose files are recognized, but cross-runtime readiness is limited.
  - The launcher can order its own processes.
  - It cannot make an external database healthy.
- Dependencies are never installed automatically.
  - Missing dependencies are reported, but the repository is left untouched.
- Ports and URLs are heuristics.
  - A conventional Vite or Next port may be wrong for a customized project.
  - An HTTP root returning 404 does not necessarily mean an API is unhealthy.
- Command classification is heuristic.
  - Failure labels help triage; they are not a formal diagnosis.

## Desktop, hotkey, and UI

- The dashboard is a local web UI, not a packaged native application.
- The WebKitGTK desktop path was implemented but not verified in this environment.
- The global hotkey is desktop integration, not core runtime behavior.
  - It requires Hyprland configuration and reloading.
  - It is isolated so missing desktop support cannot break startup/shutdown.

## AI and learning

- The optional AI provider was implemented but not exercised against a live model.
- No corpus startup required AI.
- Proposal validation rejects dangerous output, but prompt-injection resistance of an arbitrary
  external model was not evaluated.
- `learn` mode observes only processes under a selected project root.
  - It requires Linux `/proc`.
  - It cannot reliably reconstruct shell intent from forks alone.
  - Learned commands always require review before use.

## Security and privacy

- Service logs can contain secrets emitted by applications.
  - Local logs are not redacted.
  - Only outbound AI evidence is redacted.
- The loopback dashboard has no authentication.
  - Anyone able to access the local machine/port can invoke launcher operations.
- Unsafe detection is evidence-based, not exhaustive.
  - It catches explicit signals, privileged Compose patterns, deployment layouts, devices,
    and vulnerable targets.
  - It cannot prove that an unfamiliar repository is safe.

## What should come next

The highest-value work is systemic, not cosmetic:

1. Validate Docker lifecycle against a safe local Compose fixture.
2. Track process trees more strongly for daemonizing applications.
3. Expand package-manager/environment setup as an explicit, user-approved operation.
4. Improve framework-specific health endpoints instead of assuming `/`.
5. Add monorepo package/action selection to discovery and the UI.
6. Add daemon-backed live logs and health streaming while retaining CLI statelessness.
7. Test the desktop window and hotkey on a real graphical session.
